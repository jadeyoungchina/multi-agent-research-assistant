本次只读核查发现，正式实验前必须处理：

| 发现 | 对实验的影响 | 处理方式 |
| --- | --- | --- |
| 每题的 `source_files` 直接限定工作流可检索文档 | 若这些文件就是答案来源，相当于预先告诉系统去哪里找答案 | 候选文档池与 gold 来源分开，三条 RAG 流程搜索相同的整个 split 候选池，包含干扰文档 |
| recall@5 先按正确来源过滤，再取前五条 | 错排在前面的文档会被忽略 | 对真正排名前五条计算证据召回，旧口径明确改名或版本化 |
| citation precision 只检查引用 ID 是否存在 | 引用了真实但不支持结论的段落也可能得高分 | 保留 ID 有效率诊断，新增断言级支持率和引用完整性 |
| 多轮证据取各轮最大 RRF 分数合并 | 最终列表不能直接解释为同一轮的全局 top5 | 保存逐轮排名，首轮 recall@5 与最终证据覆盖分别报告 |
| 题目 schema 强制至少一个 gold 证据；ID 必须从 BENCH-001 连续排列 | 无答案题和开发/测试文件拆分受到限制 | 增加评测 schema 版本、稳定 ID、split、充分性和审核字段 |
| CLI 强制聊天、embedding 使用同一 provider | 无法直接组合 DeepSeek 聊天与 DashScope embedding | 分离配置与参数，分别记录模型和费用 |
| SDK 与外层重试可能叠加；无输出上限 | 失败时请求数和费用可能放大 | 单层重试、输出上限、逐次请求账本与预算预留 |
| 仅保存最终成功响应 usage | JSON 无效响应、失败前已发生的费用可能丢失 | 收到响应就记账，再校验；超时费用未知时保守预留 |
| Critic 补充查询排在原查询后，扩展截断可能将补充查询全部丢弃 | 多轮检索可能重复原检索 | 在开发集前修复、测试补充查询确实被执行 |
| Critic 要求完成标准原句出现在结论中 | 语义正确的改写也可能触发额外循环 | 用开发集验证并修复该机械判断；保留证据 ID 和必要覆盖检查，记录行为变更 |

**3. 真实文档与题目设计**

建议第一版围绕“AI 应用与软件工程技术资料研究”选取约 20–30 篇文档，组成约 10–15 个独立主题/文档族。候选包括 LangChain/LangGraph、Pydantic、FastAPI 的官方仓库文档；这些候选仓库有公开许可证，但每份最终纳入材料仍需核对具体路径、版本、许可证与第三方内容。文档来源见 [LangChain docs](https://github.com/langchain-ai/docs)、[Pydantic](https://github.com/pydantic/pydantic)、[FastAPI](https://github.com/fastapi/fastapi)。

每份文档登记原始 URL、固定 commit/tag、获取日期、许可证、内容 SHA-256、主题族和转换规则；保留原始快照、规范化文本及段落/页码映射。不能将 AI 改写段落标为原文。若无法确认再分发条件，则更换来源或仅提供合法获取和校验脚本。正式报告准确称为“公开真实文档上的自建评测题”，不声称题目来自真实用户。

| 题型 | 总数 | 开发集 | 保留测试集 | 检验内容 |
| --- | ---: | ---: | ---: | --- |
| 单文档事实定位 | 12 | 4 | 8 | 找到并准确概括明确事实 |
| 跨文档整合 | 12 | 4 | 8 | 联合两份以上来源给出完整回答 |
| 条件、限制与数值理解 | 12 | 4 | 8 | 不遗漏适用条件、单位、限制或步骤 |
| 版本差异与表面冲突辨析 | 12 | 4 | 8 | 识别版本/条件差异，不把历史差异当作同时成立的矛盾 |
| 给定语料证据不足 | 12 | 4 | 8 | 明确无法得出结论，避免补造答案 |
| 合计 | 60 | 20 | 40 | 中文 30、英文 30 |

每类开发集 2 中文、2 英文，测试集 4 中文、4 英文；优先独立问题，若存在翻译或改写，全部放在同一个问题组。按主题、文档族及问题组划分，再在组层面平衡类型与语言。同一材料的不同版本、近重复段落、翻译题不得跨开发与测试集。每个 split 搜索自己的完整候选池，包含无关文档；题目标签、答案来源和正确答案不传给被测系统。

制作顺序：选材和划分文档族 → DeepSeek 根据指定原文提出约 80 道候选 → 程序验证引用位置、重复和 schema → Codex 核查候选 → 真人定稿 60 题 → 保存数据卡及哈希。题目难度和数量在查看测试集模型表现之前确定。

每题保存：稳定 ID、split、语言、题型、文档族、问题、参考关键点、gold 证据位置、预期充分性、可接受的拒答行为、问题生成方式与审核状态。无答案题需核查整个候选池确实缺少所需信息，不能用“没写 gold”代替核查。所有正式参考答案应完成真人审核；若审核未完成，只能交付明确标注的初步评测。

**4. 比较矩阵与公平性规则**

| 变体 | 实验行为 | 每题聊天请求数（不含重试） |
| --- | --- | ---: |
| baseline_llm | 不检索，直接回答 | 1 |
| llm_rag | 单轮检索后生成有来源回答 | 1 |
| single_agent_rag | 计划/查询扩展，再检索并生成 | 2 |
| multi_agent_rag | Planner → Retriever → Researcher → Critic → Writer，可有最多两轮修订 | 4–8 |

主实验使用同一 Qwen 快照、相同思考模式、温度、检索候选池、embedding、chunk 参数及每轮 top-k。三条 RAG 流程使用一致的回答和引用要求。闭卷 baseline 不适用检索/引用指标，但与其他流程一起比较答案正确性、延迟和成本。不同工作流天然有不同调用量，因此报告质量与成本的权衡，不将结果解释为相同计算预算下的优劣。

先跑开发集的 5 题小样本，每类一题；验证通过后扩展到完整 20 题开发集。所有参数与流程调试只使用开发集。随后冻结代码、提示词、数据、评分规则、调用上限、执行顺序种子及主要比较假设：多智能体相对 single_agent_rag 的答案正确性变化和额外成本，其余比较作为次要观察。

正式 Qwen 矩阵：**40 题 × 4 流程 × 3 次独立运行 = 480 条 trace**，预计 960–1,440 次聊天请求，另有约 360–2,520 次查询 embedding 请求；不含语料建库、裁判和重试。三次生成均真正发出请求，不能用相同缓存答案冒充重复实验。固定温度不代表云服务输出完全确定。

补充 DeepSeek 矩阵：预算与质量检查通过后，**40 题 × 4 流程 × 1 次 = 160 条 trace**，预计 320–480 次聊天请求，另有约 120–840 次查询 embedding。此项只是单次跨模型复验，不与 Qwen 三次运行混为同一统计样本。是否执行在看其测试结果前由预算规则决定。

按问题组平衡、随机安排工作流顺序；在线延迟测量默认串行，避免不同并发造成偏差。索引预先建立，建库成本和时间单列。主延迟实验不复用查询 embedding 或生成答案缓存；文档 embedding 可按内容哈希复用。保留服务端缓存 token 信息和请求时间。

模型快照优先用可调用的固定版本；DeepSeek 别名若只能使用滚动版本，记录请求名、返回名、fingerprint（若提供）、时间和官方版本说明。版本变化时暂停该批次，分开记录；不能保证滚动 API 永久可精确复现。

**5. 指标、裁判与统计**

| 指标 | 预先固定的定义/处理 |
| --- | --- |
| 答案正确性与关键点覆盖 | 使用原文、参考关键点和统一 0/1/2 评分规则；语义改写、数值单位和适用条件都应正确处理。保留逐关键点评分，词面 F1 仅作诊断 |
| 首轮 evidence recall@5 | 在完整候选池的首轮真实前五条结果中，统计命中的 gold 证据单元比例；允许同一事实的多个等价证据，不按 gold 来源先过滤 |
| 多轮证据获取 | 每轮排名和查询独立保存；报告最终上下文覆盖、全部轮次唯一证据召回与上下文大小。跨轮合并列表不冒充同一轮排名 |
| 引用 ID 有效率 | 引用是否指向存在且已提供的证据；保留为结构性检查 |
| 断言引用支持率 | 给每个可核查断言绑定引用，判为支持/反驳/证据不足；分子为被所引证据支持的断言数，分母为带引用且需要核查的断言数 |
| 引用完整性 | 全部应有证据的事实断言中，获得有效支持引用的比例；防止通过少引用获得高分 |
| 证据不足表现 | 正确拒答/限定回答率、无依据断言率；也报告可回答题的错误拒答率，防止一律拒答得高分 |
| 工程表现 | 执行失败、截断、重试、修订轮数、模型调用数、端到端 p50/p95 延迟 |
| 费用 | 聊天/向量化/裁判/数据制作分开，报告每题、每次运行和全项目费用；实际账本与保守估计分别列出 |

不适用的指标为 N/A，并报告有效分母；闭卷流程的引用/检索为 N/A，无答案题没有 gold 证据时召回为 N/A。可回答题未提供任何必要引用时，引用完整性记 0。执行失败保留在计划矩阵和成功率分母中，主要质量指标按预先定义的失败惩罚计 0；因预算尚未执行的项目单独标记，不伪装为已测失败或完整矩阵。

裁判先用固定 schema 将全部主实验答案逐条评分，默认 DeepSeek Flash；隐藏变体、模型、文件名暗示和预期赢家。输入包括问题、答案、必要证据、评分规则，以及 evaluator 专用的参考关键点、允许答案和预期充分性；这些 gold 信息仅用于裁判，不能进入被测工作流。原文和答案中的指令作为待评数据处理。每条记录裁判模型、prompt hash、原始评分、证据依据和失败状态；裁判报错不得自动当作 0 分答案。

在开发集上用至少 20 份回答进行真人校准，分别检查关键点正确性和支持/不支持判断。建议预设类别一致率 80% 作为进入全量自动评分的最低操作门槛，同时报告样本量和分歧；该门槛不等于证明裁判可靠。低于门槛时先调整规则或扩大人工评分，不能靠换裁判挑选更好看的结果。

正式人工抽查预先抽取 20 个测试问题组的四种流程回答，共 80 份（指定一个 repeat），覆盖五类题与中英文。另行复核分歧和严重无依据回答，但这些追加样本不混入随机抽样一致率。真人审核分别记录结论，AI 辅助审核单列。DeepSeek 复验若被评分，优先以 Qwen 加人工抽查交叉评价，并单列裁判差异。

EvalScope/RAGAS 先在 5 条开发输出试运行。通过兼容性、可解释性和费用检查后，至多增加预先指定的 faithfulness 等补充指标；工具内部请求也必须经过预算控制。已有统一裁判足够时不重复为所有相近指标付费。

统计方法：先对每个问题的三次运行取均值，再计算配对差值；按文档族/问题组重采样估计 95% 区间，不能把 480 条 trace 当作 480 个独立问题。题型和语言分组标明样本数。文档族少时，区间只作探索性参考，补充逐组差异；小样本 p95 也明确不稳定。区间跨零、复杂流程更慢或质量未提升均如实报告。

预算实现要求：

1. 建立全任务共享账本，覆盖准备数据、chat、embedding、judge，以及独立 EvalScope 进程，使用统一预算协调入口。任何绕过入口的工具暂不运行。
2. 发请求前按最保守适用单价、输入 token 保守上界、明确输出上限预留费用；并发预留必须原子化。已计费用 + 未知费用预留 + 在途最大费用 + 下一请求预留不得超过可用额度。
3. SDK 禁用自动重试，应用层最多追加两次，最多三次尝试。400/401/403 等配置错误立即失败；429/可重试服务错误用有上限退避。每次尝试单独记账。
4. DeepSeek 非思考模式明确发送 `thinking: {type: disabled}`，不沿用 DashScope 的 `enable_thinking`。普通回答、结构化回答和 baseline 全部使用一致的思考设置。统一设输出上限，开发集校准后冻结；截断记录为截断，不能悄悄无限放宽。
5. 对已收到但 JSON 不合格的响应也记录真实 usage；超时/断线且 usage 未知时保留整笔预留，待平台账单核对后再释放，不能记零。缓存命中/未命中、输出和推理 token 避免重复计费。
6. 累计已用与预留达到 ¥70 时重新估算余下必要工作，优先保留主实验和人工校准；可选第二模型复验在启动前决定是否取消。到 ¥90 停发新请求，剩余 ¥10 仅用于在途/未知费用核对；不自动启动扩大规模、强模型仲裁或额外整轮实验。
7. 每完成一个实验单元立即落盘；恢复按配置哈希、题号、变体、repeat 去重。恢复完成项可复用，独立 repeat 必须新生成；不复用生成答案来伪造实验次数。
8. 正式运行前在模拟测试中验证预算边界；最终对照平台账单。客户端预留控制降低超支风险，实际结算仍取决于服务端 usage 和当时有效价格；存在无法界定的价格或 token 上界时先停发该请求。

DeepSeek 当前 API 默认开启思考，输出默认上限较大，不能只更换模型名而忽略这些参数。接口、usage 与参数依据：[DeepSeek Chat Completions 文档](https://api-docs.deepseek.com/zh-cn/api/create-chat-completion/)。
